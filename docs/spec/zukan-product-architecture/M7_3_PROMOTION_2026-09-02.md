## Delta

Implement a provider-neutral `ProgramHandoverAcceptance` contract with a D1-first append-only adapter and deterministic source tests.

The acceptance request MUST bind:

- tenant/workspace scope;
- immutable M7.1 plan identity;
- immutable M7.2 offer identity;
- current source Program/revision;
- target Program/continuation scope;
- authenticated incoming actor identity;
- current incoming target-scope authorization;
- current outgoing source-scope authorization;
- acceptance idempotency key;
- actor/audit ref and accepted-at timestamp.

Rules:

1. The actor accepting MUST exactly match the offer's `intendedIncomingActorRef`.
2. Incoming actor must be currently authorized/eligible for the target Program/workspace scope. Unknown, revoked, stale or scope-mismatched identity fails closed.
3. Re-read the offer, immutable plan and current source/target bindings at acceptance time. Missing/stale/mismatched bindings fail closed.
4. The offer must still be `pending_acceptance`; an already accepted/conflicted/non-pending offer cannot create a second logical acceptance.
5. Re-read outgoing source responsibility at acceptance time. If the outgoing actor is no longer authorized, do not complete acceptance; require a new valid offer from a currently authorized outgoing actor.
6. Acceptance is explicit. Do not infer acceptance from membership, login, opening a link, inactivity or elapsed time.
7. Persist one append-only acceptance receipt. Do not rewrite the M7.1 plan or M7.2 offer payload.
8. The source-only terminal state is `accepted_pending_apply` (or an equivalent unambiguous name). It MUST NOT be named or exposed as `completed`, `transferred`, `live`, or equivalent.
9. Responsibility transfer in M7.3 means a verified accepted transfer intent/receipt only. Actual Program role/ownership mutation belongs to M7.4 staging execution.
10. No outgoing actor removal in M7.3. Preserve outgoing provenance. Actual removal/change follows only after the transfer is successfully applied in the later runtime slice.
11. Do not carry participant rows, consent grants, Review decisions, publication approvals, visibility state, private payloads, or duplicated Place/Record rows.
12. Same idempotency key + same acceptance payload converges to one logical acceptance including concurrent retry. Same key + different payload fails closed.
13. Partial/write failure never reports acceptance or transfer preparation as successful.
14. Source/migration definitions may be added, but no staging/production migration application, route/UI activation, target Program mutation, permission mutation, customer send, secret/DNS/IAM/billing change or production release is authorized.

Do not add decline/cancel/expiry policy in this slice unless current canonical source already has an adopted contract requiring it. M7.3 proves explicit acceptance only; do not invent lifecycle policy to make the state machine look complete.

## Required negative/property fixtures

At minimum:

- intended incoming actor accepts once;
- wrong actor cannot accept;
- incoming actor unknown/revoked/scope-mismatched fails closed;
- outgoing actor revoked before acceptance fails closed;
- missing/stale plan or offer identity fails closed;
- non-pending/already-accepted offer does not create a second acceptance;
- retry/concurrent retry converges to one logical acceptance;
- same idempotency key + different payload conflicts;
- accepted receipt references the exact immutable plan and offer;
- target Program responsibility remains unchanged in M7.3 source-only tests;
- outgoing actor is not removed in M7.3;
- participant/consent/Review/publication/visibility state is not copied;
- write/transaction failure never returns accepted/completed.
