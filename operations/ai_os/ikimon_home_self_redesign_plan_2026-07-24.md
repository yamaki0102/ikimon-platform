# ikimon.life ログイン後 Home／「自分」再設計計画

- 作成日: 2026-07-24
- 対象: ログイン後 Home（`/`）／自分（`/profile`）／共通ヘッダー
- 基準コミット: `31e3e46e`
- 状態: Wレビュー反映済み・実装判断可能
- 目的: ログイン後に「何かしよう」と思える理由を、本人の写真・場所・反応・次の活動から作る

## 1. 結論

現在の Home は、撮影を促す説明カードを並べた「入口案内」であり、ログイン後に戻ってくる価値を返していない。Home の役割を次のように変更する。

> Home は、本人の記録に起きた変化と、今やる一つを返す場所。

撮影は引き続き下部ナビ左端の常設アクションとする。ただし、Home の本文で毎回「撮る」を主役にしない。本人の状態に応じて、未完了の下書き、前回の写真、思い出、届いた反応、場所の続き、参加中の活動のどれか一つを最上位にする。記録が0件のときだけ、本文の主行動を「撮る」にする。

「自分」は記録ダッシュボードから、次の役割へ絞る。

> 「自分」は、プロフィール・共有先・参加・公開範囲・役割・設定を管理する場所。

写真一覧は「記録」、場所の履歴は「場所」、今日の続きは Home に置く。`/profile` に記録・場所・図鑑・履歴・成長・貢献・設定を全部積む現行構成は廃止する。

## 2. 最上位の成果と論点分解

最上位指標は `ログイン後60秒以内の意味ある行動率` とする。意味ある行動は、撮影開始だけでなく、下書き再開、本人記録の閲覧、場所の再訪、反応の確認、参加中活動の再開を含む。

### 2.1 MECEな問題分解

1. 本人の状態が見えない
   - 本人の写真がファーストビューにない
   - 前回の具体的内容が見えない
   - 記録後に何が変わったか分からない
2. 次の行動が状態と無関係
   - 全員に同じ「撮る」を出している
   - 下書きがあっても0件向けCTAと同時表示される
   - 場所・イベント・反応が行動候補になっていない
3. 戻る理由がない
   - 思い出、変化、反応、続きがない
   - 写真が時間・場所・人に束ねられていない
4. 情報構造が重複している
   - Homeと「自分」がどちらも個人ダッシュボード化している
   - 下部「自分」とヘッダーのプロフィールアイコンが重複している
   - 「記録」「場所」「自分」の責務が混在している
5. 継続を阻害する危険な模倣
   - 星評価、ランキング、投稿数ポイントは地域の悪評固定やスパムを生む
   - 正確な位置や行動履歴の強調は、自宅・学校・希少種の安全を損なう
   - 一般SNS型フィードは他人比較を主目的に変える

## 3. 現状の原因

### 3.1 Home

正本は次の呼び出し経路である。

`platform_v2/src/app.ts`
→ `platform_v2/src/ui/landingTop.ts`
→ `platform_v2/src/ui/landingHomeState.ts`

`renderMember()` が次を独立に描画している。

- `home-member-action`: 全ログインユーザーへ常時「今日は何を残しますか？／撮る」
- `home-continuation`: IndexedDBに撮影下書きがあると表示
- `home-empty-state`: `ownItems.length === 0` なら「最初の記録／撮る」

下書きの有無と保存済み記録0件は排他的でないため、添付画面では「撮る」「続き」「撮る」が同時に出る。下部ナビの「撮る」も含めると、同じ目的の入口が4つある。

一方、`LandingSnapshot` が持つ次の情報は、現在のログイン後 Home で十分に使われていない。

- `myFeed`: 本人の写真・動画・音・メモ
- `myPlaces`: 本人が関わった場所
- `nearbyEvents`: 関連イベント
- `habit`: 直近の記録状況
- `dailyDashboard`: 日次候補、季節候補、再訪候補
- `regionalStory`: 場所の次の見方

つまりデータ不足が主因ではない。表示優先順位と状態設計が主因である。

### 3.2 「自分」

正本は `platform_v2/src/routes/read.ts` の `renderSelfProfileHub()` である。現行は次を一ページに連結している。

- 最後に保存した記録
- 4枚のチャンネルカード
- プロフィール
- 自分の記録史
- 資料
- Life List
- 場所の物語
- 履歴
- 成長
- 集計
- 地域への貢献
- アカウント設定

このため、「自分」が個人情報の管理画面なのか、記録一覧なのか、図鑑なのか、成果レポートなのか判別しにくい。さらに「記録」「場所」「Home」と内容が重複している。

### 3.3 重複・shadow実装

`platform_v2/src/ui/landingTop.ts` と `platform_v2/src/routes/read.ts` には、現在のルートから使われない旧Home系レンダラーやスタイルが残る。今回の実装では、これらを再接続せず、現行正本の `landingHomeState.ts` と `renderSelfProfileHub()` を最小変更する。不要コードの大規模削除は別タスクにする。

### 4.1 ikimon.lifeに必要な独自統合

ikimon.lifeは写真保管でも口コミサイトでもない。勝ち筋は次の一連のループである。

`写真を残す`
→ `自分の時間に残る`
→ `場所の変化として残る`
→ `誰かの反応や確認が返る`
→ `次に見ること・参加することが一つ生まれる`

この5段をHomeで一度に説明せず、ユーザーの実データから一つずつ見せる。

## 6. ログイン後 Home の再設計

### 6.1 基本原則

- 画面本文の主行動は常に一つ
- 主行動はユーザー状態で変わる
- 1画面目は説明文ではなく本人の写真または具体的な状態
- 値がないセクションは出さない
- 「0件」「未記録」「名前待ち」を見出しにしない
- 他人の一般フィードはHomeへ置かない
- 下部「撮る」が常時あるため、保存済み記録がある人へ撮影CTAを重ねない

### 6.2 ファーストビュー状態機械

P0の優先順位は次で固定する。最初に一致した一状態だけを表示する。本人の記憶を継続動機の基盤にし、他者反応はHeroを奪わない。

1. `draft_resume`
   - 条件: IndexedDBに有効な下書きがある
   - 表示: 同一ユーザー／同一認証継続であることを確認できた場合だけ、下書きの実サムネイルと撮影日時
   - 共有端末または所有者を確認できない場合は、画像・場所を出さず、汎用の再開案内だけ
   - 主行動: `保存の続きをする`
   - 補助: `あとで`。破棄は詳細内で確認付き
2. `recent_memory`
   - 条件: 保存済み記録がある
   - 表示: 最新または今日に関連する本人写真を大きく表示
   - 見出し例: `7月20日・都田で残したこと`
   - 主行動: `見返す`
   - 安全な公共場所だと確認できる文脈がある場合のみ補助: `同じ場所で撮る`
3. `active_context`
   - 条件: 参加中イベント、追っている場所、次の確認事項がある
   - 表示: 場所または企画の実写真と次の一手
   - 主行動: `続きを見る`
4. `first_record`
   - 条件: 上記がなく保存済み記録もない
   - 表示: 短い一文と1つの主CTA
   - 見出し: `最初の1枚を残す`
   - 主行動: `撮る`
   - 補助行動: `端末の写真から選ぶ`

初回状態でも、本文中の撮影CTAは一つだけにする。下部ナビの「撮る」はグローバル操作として残す。

### 6.3 ファーストビュー下の優先セクション

最大4セクション。該当データがないセクションは詰めずに消す。

1. `最近`
   - 本人写真を2列グリッドで最大6件
   - 日付と安全な場所ラベルだけ
   - 「すべて見る」は `/records?view=mine`
2. `見返す`
   - この日、同じ月、前回のイベント等から1コレクション
   - 自動生成理由を短く表示
   - 他人の写真を混ぜない
3. `場所の続き`
   - 本人が記録した場所を最大2件
   - 最後の写真、最終訪問、最近の変化、次に確かめることのどれか一つ
   - 正確な位置は本人画面だけ。カードには粗い地名を基本とする
4. `届いたもの`
   - P1で追加。未読の確認、コメント、共有グループの追加写真
   - Heroにはせず、本人の記憶に付加されるボーナスとして扱う
   - 数や順位を強調せず、権限確認済みの専用read modelから表示
   - 反応者名は、表示同意と関係性が確認できるまで出さない
5. `次の活動`
   - 参加中または本人の場所・記録と関係するイベントだけ
   - 一般的な近隣イベントの羅列はしない

同時に5つある場合は、`届いたもの` と `次の活動` のうち本人の記録・場所との関連が強い方を優先し、画面全体を最大4セクションに抑える。未読数の多さだけで順位を上げない。

### 6.4 モバイル骨格

```text
┌ ロゴ                    未読がある時だけ ● ┐
│ [本人の写真／下書き／届いた変化]             │
│ 7月20日・都田で残したこと                    │
│                       [見返す]                │
├ 最近                                  すべて │
│ [写真] [写真]                                │
│ [写真] [写真]                                │
├ 場所の続き                                  │
│ [場所写真] 都田総合公園   前回から12日       │
├ 届いたもの／次の活動（ある時だけ）           │
└ 撮る ｜ 場所 ｜ 記録 ｜ 自分                 ┘
```

### 6.5 デスクトップ

- 情報構造と語彙はモバイルと同じ
- 左側に写真主役のファーストビュー、右側に次の一手を置ける
- 最近の記録は3列
- モバイルにないダッシュボード指標を追加しない

## 7. 「自分」の再設計

### 7.1 最上部

- アバター、表示名、短い紹介
- `公開プロフィールを見る`
- `プロフィールを編集`
- 本人にしか見えない画面であることを明示

写真グリッドや「最後の記録」は置かない。下部「記録」から一手で開けるためである。

### 7.2 セクション

1. `共有先`
   - 家族、学校、チーム、イベント等を同じ「共有先」モデルで扱う
   - 各共有先に `誰が見られるか` と `自分の役割` を表示
   - P0では既存のイベント参加・公開設定への導線だけ
   - 実在する共有・参加先がない場合、セクション自体を表示しない
   - 独立した招待制共有グループはP2
2. `参加している`
   - 参加中イベント、継続企画、担当ロール
   - 活動詳細へ遷移
3. `公開と位置`
   - 新規記録の初期公開範囲
   - 正確な場所を見られる範囲
   - 自宅・学校・希少種等の保護状態
4. `役割`
   - 通常利用者、主催者、学校、専門家等、実際に権限がある役割だけ
   - 権限がない役割の宣伝カードは出さない
5. `設定`
   - 通知、言語、アカウント、ログアウト

### 7.3 現行項目の移動先

| 現行「自分」の項目 | 移動先 |
|---|---|
| 最後に保存した記録 | Homeの状態カード／記録 |
| 最近の記録 | 記録 |
| 自分のフィールド／次に行く場所 | 場所 |
| Life List／自分の図鑑 | 記録内コレクション |
| 自分の記録史／履歴 | 記録の年・月表示／Homeの思い出 |
| 成長・貢献集計 | 記録内の任意レポート。Homeや自分の主役にしない |
| 名前待ち | 記録のフィルター。主見出しにしない |
| プロフィール編集・ログアウト | 自分に残す |

## 8. ヘッダーとナビ

- ロゴはHomeへ戻る
- モバイルでは下部「自分」があるため、ヘッダーのプロフィールアイコンを削除
- 通知ベルは未読がある時だけ状態を持つ。通知0件でも入口自体を残すかは実装前QAで判断する
- 検索はP1で、写真・場所・メモを横断する単一検索として検討
- 下部ナビ `撮る｜場所｜記録｜自分` は維持
- `撮る` はactive routeを持たない

## 9. 実装フェーズ

### P0: 意味のない重複をなくし、本人の写真へ置き換える

DB変更なし。1本の実装PRにまとめる。

1. `landingHomeState.ts`
   - `selectMemberHomeState()` を純関数で追加
   - P0は `draft_resume / recent_memory / active_context / first_record` の4状態
   - 最上位状態を排他的に一つだけ描画
   - 保存済み記録がある人の常設「今日は何を残しますか？」を撤去
   - `myFeed`、`myPlaces`、`nearbyEvents`、`dailyDashboard` を使い、本人写真中心へ変更
2. IndexedDB下書き
   - サーバー描画後にカードを追加表示する方式をやめる
   - クライアントで状態を確定して、Heroを`draft_resume`へ置換
   - 現行の全ユーザー共通キー `latest` をそのまま表示判定に使わない
   - 下書きへ所有者partitionと一度限りの認証継続tokenを付け、現在のセッションと一致した下書きだけをロード
   - ログイン、ログアウト、アカウント切替で他partitionを画面状態から除去
   - guest撮影は、同じ認証復帰tokenを持つ場合だけ新しいアカウントへclaimする
   - Object URLは画像差し替え、モーダル終了、DOM破棄の各時点で即時解放し、`unload`だけに依存しない
   - サーバーHeroからの差し替えでCLSが出ないよう、領域を先に確保
3. `renderSelfProfileHub()`
   - プロフィール、参加、公開と位置、役割、設定に縮約
   - 記録・場所・集計カードを各正規面へ移す
4. `siteShell.ts`
   - モバイルHomeの重複プロフィールアイコンを削除
   - 未読表示と下部ナビの責務を整理
5. i18n
   - 日本語を正本として4ロケール同時追加
   - テンプレート直書きを増やさない
6. テスト
   - 状態選択、排他表示、0件、記録あり、下書き、反応あり、場所あり
   - Home本文の主CTAが一つ
   - `/profile` に記録グリッドや内部状態見出しがない
   - 375／390／768／1440pxの視覚QA

### P1: 戻る理由を強化

DBスキーマ変更なしを優先する。

- 本人記録への新しい反応をHome用read modelへ集約
- 反応はHero状態にせず、本人の記憶へ付加する条件付きセクション
- 位置・機密画像を含まない専用通知スキーマを使い、クライアントで特権データをJOINしない
- 過去の同日・同月・同じ場所を出す「見返す」クエリ
- 記録ライブラリの写真／時間／場所／公開範囲フィルター
- 本人が追っている場所・種・イベントから次の活動を選ぶ
- Homeの横断検索

### P2: 限定共有

別のプロダクト判断とプライバシー設計が必要。P0/P1へ混ぜない。

- 家族、学校、チーム、イベントを扱える招待制「共有先」
- 個人記録と共有記録を明確に分離
- 投稿時に見える相手を常時表示
- 管理者、投稿者、閲覧者の権限
- 脱退・削除・招待取消・子どもアカウントの安全設計

P2でDB変更が必要なら、migrationは別承認とする。

## 11. プライバシーと安全

- Homeは本人画面でも、カード上の場所名は粗い地名を基本とする
- 正確な位置は詳細を開いた本人にだけ表示
- Home用read modelで `homePreviewPolicy: photo | photo_without_place | masked | excluded` をサーバー側で決定する
- 自宅、学校、私有地、希少種、センシティブな場所は、Hero・見返す・場所の続き・次の活動・自動生成コレクションの推薦元から除外する
- `最近`へ出す場合も、`homePreviewPolicy` に従って場所ラベルを消すか、写真を安全な代替表示へ変える
- 画像背景から再特定される危険がある記録はHomeに自動選出せず、「記録」から本人が明示的に開く
- 安全な再訪先は「公共公園だけ」に固定せず、既存の場所管理・公開・立入条件から安全性を判定する
- 公開プロフィールへHome状態、下書き、未読、参加予定、訪問頻度を出さない
- 子ども、学校、自宅、私有地、希少種は既存の位置保護を維持
- 共有先は既定非公開。個人から共有への移動は明示確認
- 反応通知に正確な位置や画像解析結果を埋め込まない
- 「近くで撮る」「再訪」を危険な場所・時間へ誘導しない
- ランキング、賞品、競争による危険移動や過剰投稿を作らない

## 12. 計測

既存分析基盤だけを使う。画像内容、正確な位置、個人名を送らない。

### 主指標

- `home_meaningful_action_60s`: Home表示後60秒以内に意味ある行動へ進んだ率。単純閲覧と完了行動を別集計する
- `home_record_revisit_rate`: 本人記録を開いた率
- `draft_resume_completion_rate`: 下書き再開から保存まで
- `place_continue_rate`: 本人の場所の続きへ進んだ率
- `response_open_rate`: 届いた変化を開いた率
- `return_7d`: 7日以内の再訪

### ガードレール

- `capture_open_rate` を悪化させない
- カメラ成功率、保存完了率を悪化させない
- Home LCP／INP／CLSを悪化させない
- 通知開封を増やしても、通知OFF率や離脱を増やさない
- 公開範囲変更、位置情報問い合わせ、誤共有報告を増やさない

### 採用条件

- Home本文の主CTAが常に1つ
- 実装前に2週間以上のベースラインを取得する
- `記録0件 / 1-5件 / 6件以上`、下書き有無、参加文脈有無でコホートを分ける
- 意味ある行動を `保存完了・下書き完了・安全な活動再開`、`記録閲覧・場所閲覧` に分け、前者を主評価、後者を副評価にする
- 60秒以内の主評価行動率が現状比30%以上改善
- 本人記録の再閲覧率が現状比20%以上改善
- 撮影開始率・保存率に有意な悪化がない
- 7日再訪率が現状比10%以上改善
- 誤共有・位置公開のP0/P1インシデントが0

### 不採用・ロールバック条件

- 写真中心化でLCPが許容値を超える
- 下書きの消失、二重保存、Object URLリークが発生
- 共有／反応表示から非公開情報が推測できる
- Homeからの撮影開始が大きく低下し、他の意味ある行動で補えない
- 空データ時に説明カードが再び複数並ぶ

## 15. Wレビュー採否

### 実行結果

- Claude: `complete`、`claude-opus-4-8`
- Gemini: `complete`、`gemini-3.5-flash`
- Gemini失敗候補: なし
- Geminiモデル文書確認: 不要
- 証跡: `operations/ai_os/external_review_evidence/2026-07/ikimon-home-self-redesign-20260724/20260724-050053/`

### 採用

- 他者反応をHero優先順位から外し、本人の記憶を恒久的な継続エンジンにする
- P0の状態機械を4状態へ限定し、反応集約をP1へ移す
- Homeの全写真・場所サーフェスへサーバー側安全ポリシーを適用する
- 自宅、学校、私有地、希少種、センシティブな場所を自動再訪提案から除外する
- 公開プロフィールへ下書き・未読・参加予定・訪問頻度が漏れないテストを追加する
- IndexedDB下書きをユーザー／認証継続単位で隔離し、共有端末のアカウント切替をテストする
- Object URLを`unload`だけに頼らず、画像差し替え・終了・DOM破棄時に解放する
- P0で実体のない「共有先」は表示しない
- 計測へ事前ベースライン、コホート分割、完了行動と閲覧行動の分離を追加する
- 反応通知は専用の安全なread modelを使い、反応者名は同意確認まで表示しない

### 保留

- 招待制の家族・学校・チーム共有はP2の専用プライバシー設計まで保留
- 反応者の実名表示は、双方の表示同意と子どもアカウント規則が決まるまで保留
- 過去同日・同月の自動「見返す」は、安全選出とread modelを整えるP1へ保留

### 不採用

- 本人専用Homeでも希少種写真を一律で強くぼかす案
  - 本人の記録を本人から隠し、見返す価値を損なう。代わりに自動Hero・再訪提案から除外し、必要な面では安全な代替表示をサーバー側で決める
- 再訪先を公共公園だけに限定する案
  - 公共施設以外にも同意済み・安全な地域活動場所がある。既存の立入条件と公開ポリシーで判定する
- Reactの`useEffect`等、現行Alpine.js／vanilla DOMに存在しないフックの使用
  - 目的である確実な解放は採用し、現行技術では画像差し替え・モーダル終了・DOM破棄イベントで実装する
- ハッシュ化したuserIdだけで下書き隔離が完成するという案
  - ハッシュは暗号化でも認可でもない。所有者partition、認証継続token、セッション切替時の除去を組み合わせる
