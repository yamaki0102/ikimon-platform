いきもの記録サービスの、自社運営・同意ベースの防御的セーフガード監査として本記録をレビューします。以下、指定形式で。

---

## 1. 採用すべき点

- **Home最上位の排他状態化**（`draft_resume / recent_memory / active_context / first_record`）。「撮る／続き／撮る」の重複を一状態へ畳んだのは正しい。UXと privacy 両面で「本人の次の一手」が一意になる。
- **下書きの partition + 所有者バインド**：`latest:user:<userId>` / `latest:guest:<token>` へ分離し、キーと `ownerKey` の**両方一致**でのみ表示、旧共通キー `latest` を自動claimしない方針は方向として正しい。
- **センシティブ記録をHome heroから除外**し、記録一覧への安全導線だけ残す設計。
- **スコープ規律**：「新しい投稿基盤は作っていない」「既存 `/record` 保存フローへ接続」。過剰実装を避けた点は評価。
- **カメラ失敗系の視覚テスト網羅**（拒否／非対応／MediaStream停止）と 4 ロケール同時追加。

## 2. 重大な懸念

- **C1（最重要）：privacy保証が「文章」であって「テスト」でない。** §2 の隔離・§4 の論点はいずれも散文の主張で、§3 の検証は**visual regression 中心**。別所有者下書き・カメラ系も「28件成功」の視覚比較であって、*どのユーザーに何が保存・表示されたか*を assert する振る舞いテストが見当たらない。視覚テストは「別アカウントの写真が誤って本人に紐づいた」誤保存を検出できない。
- **C2：センシティブ判定の fail-safe が未記載。** AI処理中／分類未確定の記録がHomeに来たとき、写真・タイトル・場所を出すのか出さないのか。**default-deny（未確定=センシティブ扱いで非表示）**でなければ、分類完了前の窓で漏洩する。
- **C3：旧 `latest` の残渣ライフサイクル未証明。** 「自動claimしない」は入口の話。既存端末に残る旧下書きが**いかなる経路でも表示・claimされない**保証と、掃除（save/logout時の削除）が示されていない。
- **C4：guest token のセキュリティ特性が未定義。** 乱数源（CSPRNG か）、保存場所、TTL、セッション単位かどうか。共有端末で guest A→guest B と使ったとき B が A の下書きを見ないことが、token 設計に依存するのに要件化されていない。
- **C5：認証復帰後の保存の end-to-end 機能テストが無い。** 本改修の回帰の芯は「guest撮影 → サインイン → rekey → `/record` 保存」で、正しい所有者に保存され guest partition が消える、というパス。ここが視覚テストではカバーされない。
- **C6：「安全な場所ラベル」の導出が未定義。** ラベル生成規則次第で自宅周辺の粗い位置が滲む。`myPlaces`／「関わっている場所」／`nearbyEvents` の Home 露出も同根。

## 3. P0で変更すべき仕様（staging前の必須ブロッカー）

1. **default-deny の明文化と実装＋テスト**：分類未確定・失敗・pending は Home で写真/タイトル/場所を出さない。境界テスト必須。
2. **機能（非視覚）blocking test を追加**：
   - 同一ブラウザでユーザA下書きがユーザBに**非表示**であることの assertion。
   - **guest↔guest 隔離**（2セッションで相互不可視）。
   - **旧 `latest` がどのユーザーにも表示・claimされない**。
   - **save-after-rekey 正当性**：正しい userId に保存され、保存後 guest partition が消える／再表示されない。
   - **logout非露出**：ログアウト後に本人下書きが次ログイン/次guestへ漏れない。
   - **token不一致で非claim**（現状 visual のみ→振る舞い assert 化）。
3. **guest token の要件定義**：CSPRNG・セッション単位・TTL・save/logout でクリア、をドキュメントとコードで固定。
4. **端末画像選択（ギャラリー/ファイル選択）の保存回帰確認**：§4 で論点化されているのに §3 の検証項目に明示が無い。テストを追加または既存カバレッジを明記。

## 4. P1以降に回すべき仕様

- IndexedDB の at-rest 暗号化・eviction 強化（partition しても共有端末＋devtools の残余リスク。P0の隔離が担保されていれば後回し可）。
- 旧 `latest` エントリの**能動的マイグレーション/削除**（本人端末で同意ベースに掃除）。P0 は「表示しない」で足り、削除は後続。
- 欠落 i18n キーの lint/テスト（fallback で内部語 `record` が露出しない保証の自動化）。
- 「安全な場所ラベル」ヒューリスティクスの精緻化。

## 5. 最終推奨

**条件付き Go（現状のままでは staging へ進めない）。**

実装の設計方向（排他状態・partition・スコープ規律）は妥当で、採用に足る。ただし本記録の privacy/隔離の中核は**散文の主張に留まり、検証は視覚回帰に偏っている**。誤保存・誤表示という最も痛い漏洩は視覚テストでは捕まらない。

したがって **§3 の P0（default-deny＋機能 blocking test 群、特に「クロスユーザー非表示」「save-after-rekey」）が green になるまでは staging/production を保留**。P0 完了後は、記録に実SHA・staging authenticated QA 結果・保存/復帰の機能テスト証跡を追記して再確認、という順序を推奨します。
