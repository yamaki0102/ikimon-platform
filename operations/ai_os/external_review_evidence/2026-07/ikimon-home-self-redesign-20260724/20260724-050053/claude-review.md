- **排他的な単一状態＋本文主CTA一つ**：draft/continuation/empty が排他でないため「撮る・続き・撮る＋下部撮る」で入口が4重化していた問題を、状態機械で構造的に解消する方向は正しい。「値がないセクションは出さない」「0件を見出しにしない」も良い。
- **星評価・ランキング・投稿ポイントの明示的不採用**：地域の悪評固定・スパム・希少種や自宅への危険誘導を避ける判断は、civic/自然観察サービスとして必須の防御。§4 の「見た目ではなく再訪理由で借用する」フレーム、§11 の粗い地名デフォルト・精密位置は本人詳細のみ、も方向として支持。

## 2. 重大な懸念

1. **`new_response` を優先順位2位（recent_memory より上）に置く設計**：動機ループとして「他者の反応」を本人の記憶より上位に出すと、比較・承認・通知駆動という本計画自身が避けたい引力を最上位に据えることになる。低密度な civic サービスでは反応が長期間ゼロになりやすく、外部反応に再訪価値を依存させるとループが折れる。**自己生成される recent_memory / 見返すが恒久エンジン、反応はボーナス**という順序が本筋。
2. **反応表示のプライバシー**：「○○さんが名前を確かめました」は反応者の身元を本人（子どもを含む）画面へ露出する。子どもの記録を誰が閲覧・反応しているかが可視化され、ハラスメント・特定の導線になり得る。反応者側が「名前で表示されること」に同意しているか（consent モデル）が未定義。
3. **Home 面での位置再特定リスクが hero/grid/場所の続きに未適用**：§11 は「詳細のみ精密位置」だが、`最近`グリッドのサムネイル、`場所の続き`の「都田総合公園・前回から12日」、訪問頻度の組合せは、粗い地名でも自宅・学校・生活動線・希少種を再特定し得る。**§11 の保護が Home の新規サーフェス（hero/grid/場所カード/サムネイル）に及ぶ規則が明文化されていない**。監査観点（子ども・学校・自宅・私有地・希少種）の中核リスク。
4. **P0 と状態機械の不整合**：§6.2 は5状態だが、P0（§9-1）で使うのは `myFeed/myPlaces/nearbyEvents/dailyDashboard` のみで反応は含まれず、反応集約は P1（§9-P1）。よって `new_response` は P0 では常に空となり、優先度2に配線すると暗黙に recent_memory へ降格する。実装者が常時空の状態を2位に置く危険。
5. **`共有先`セクションの P0 空問題**：P0 は既存イベント参加/公開設定への導線だけで招待制共有は P2。多くのユーザーで `共有先` はほぼ空になり、本計画の「空セクションを出さない／0件を見出しにしない」原則に自己矛盾する。
6. **計測の設計不足**：`home_meaningful_action_60s` は「本人記録の閲覧」まで意味ある行動に含むため、Home をスクロール面に最適化しても数値が上がり得る（civic な新規記録・同定確定が薄まる）。加えて**ベースライン値・観測期間・サンプル・コホート分割（0件層と多数層で挙動が正反対）が未定義**のまま「30%改善」を採用条件にしている。
7. **未検証の外部依存**：反応 read model と `/api/v1/me/area-subscriptions` の存在・形状は「調査して再利用」の仮定。無い場合 `new_response`/`active_context` は新規インフラを要し「P0 DB変更なし」と衝突する。

## 3. P0 で変更すべき仕様

- **`new_response` を P0 の状態機械から外し P1 に明記**。P0 は `draft_resume / recent_memory / active_context / first_record` の4状態で出荷。反応 read model の有無を実装前に確認し、無ければ `active_context` も既存 area-subscriptions/event participants で埋まる範囲に限定。
- **センシティブ位置の Home 全面適用規則を追記**：自宅・学校・私有地・希少種・精密座標タグの記録は、詳細だけでなく **hero・`最近`グリッド・`場所の続き`・サムネイル・自動生成コレクションすべてで除外またはマスク**する。これをサーバ側テストで固定化。
- **公開面への漏洩をサーバ側で禁止するテスト**：`/profile/:userId` に Home 状態・下書き・未読・参加予定・訪問頻度が出ないことを、共有 read model（`readModels.ts`）経由の再利用も含めアサート。
- **`draft_resume` の描画規約**：サーバ hero→クライアント差し替えのフラッシュ/CLS を避けるため、離脱前提のプレースホルダで領域確保。Object URL 解放（§9-2）は維持しつつ、共有端末でのショルダーサーフィン前提でサムネイル表示の是非を実装前 QA 項目に。
- **`共有先` の P0 空挙動を定義**：既定のみのときは節を畳む（無セクション）ことを明示し、原則との矛盾を解消。
- **計測の採用条件を運用可能に**：ベースライン値の事前取得、記録件数コホート別評価、「意味ある行動」の重み付け（新規記録・同定確定を上位、単純閲覧を下位）を定義してから 30% 目標を設定。

## 4. P1 以降に回すべき仕様

- **P1**：`new_response` 状態の有効化と反応集約 read model、`見返す`（同日/同月/同場所）クエリ、記録ライブラリの写真/時間/場所/公開範囲フィルタ、`次の活動`選定、横断検索。いずれも DB スキーマ変更なしを優先という現行方針を維持しつつ、read model 追加の可否を先に判定。
- **P2**：招待制`共有先`、個人/共有記録の分離、投稿時の可視相手常時表示、管理/投稿/閲覧の権限、脱退・削除・招待取消。**特に子どもアカウントの安全設計（誰が子の記録を見られるか、反応者身元の露出、退出時のデータ扱い）は専用プライバシー設計＋migration 別承認**という現行の切り分けを支持。反応者身元の consent モデルはここで確定。

## 5. 最終推奨

**条件付き採用**。Home の返り値化・排他的単一CTA状態機械・星評価/ランキング不採用・粗い地名デフォルト・P0/P1/P2 の分離という骨格は妥当で、P0 を進める価値がある。ただし出荷前に以下を必須条件とする：

1. `new_response` を P0 から外し4状態で出荷（動機ループは自己生成の記憶を基盤に据える）。
2. センシティブ位置マスクを Home 全サーフェス＋サムネイルへ適用し、サーバ側テストで固定。
3. 公開プロフィールへの Home 状態/下書き/未読/参加漏洩をサーバ側テストで禁止。
4. 反応表示の身元露出（子どもの記録を誰が見たか）の扱いを P2 の consent 設計まで留保、P0 で先行露出しない。
5. 計測のベースライン・コホート分割・「意味ある行動」重み付けを定義してから採用/不採用条件を確定。

これらを満たさない場合は**保留**。特に(2)(3)(4) は監査観点（子ども・学校・自宅・私有地・希少種・限定共有）の中核であり、未対応での P0 出荷は非推奨。
