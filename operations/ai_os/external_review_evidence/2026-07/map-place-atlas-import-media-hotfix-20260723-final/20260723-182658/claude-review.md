以下、レビュー対象本文と提示された証跡のみに基づく最終レビューです（ツール不使用）。

## 1. 採用すべき点

- **根本原因の特定が正確**。`/derived/import/` は R2 backed の確定サイズ派生物であり、汎用 `/derived-transform/` 経路がこれを解決できない、という因果は本番の 200/404 再現と整合しています。対症ではなく経路ミスマッチの本質を突いています。
- **失敗先行テスト**を伴い、変更前赤・変更後緑を確認済み。回帰テスト（制御文字拒否・非 display 資産は迂回しない）も同梱されており、修正意図がテストで固定されています。
- **変更が最小1条件**で、他 `/derived/` の transform 挙動は不変。ブラスト半径が極小です。
- **信頼境界を広げていない**：戻り値は同一オリジンの相対パスであり、外部/絶対/protocol-relative を新規許可していません。実質的な最悪ケースは 404 に留まります。
- 移行・シークレット・DNS・権限・書込・プライバシー契約の変更なしで、exact-SHA ゲート／staging dry-run／本番直リンク 200 まで通っている点は、ホットフィックスとして健全です。

## 2. 重大な懸念

- **ガード順序への暗黙依存（最重要）**：新しい早期 `return url;` の安全性は、制御文字・protocol-relative・same-origin 検査が**この行より前で必ず実行される**ことに全面依存します。本文は「safeguards remain unchanged」「制御文字は拒否」と主張していますが、excerpt では前段ガードの位置が確認できません。`/derived/import/<CTRL>…/display.webp` が `startsWith`/`endsWith` を満たして早期 return に到達する順序でないことが、コード上の必須確認事項です。
- **`endsWith("/display.webp")` の脆さ**：クエリ文字列やフラグメント付き URL（`…/display.webp?v=…`）は条件を外れ transform 経路に落ちて再び 404 になります。imports が常に素の相対パスである前提が崩れると再発します。
- **レスポンシブ喪失**：`width` を無視して固定 display.webp を返すため、この関数で srcset の複数幅を生成している場合、全幅が同一 URL になり responsive 配信が失われます（回帰ではなく性能劣化）。

## 3. P0 で変更すべき仕様

- 上記「ガード順序」を**コードで確認**し、制御文字/正規化検査が新条件より前段にあることを保証（無ければ順序修正）。テストは制御文字を拒否と主張していますが、これは実装配置の裏取りが必要な P0 事項です。ここが担保されていれば P0 は他になし。

## 4. P1 以降に回すべき仕様

- `endsWith` を**パス末端の厳密判定**（クエリ/フラグメント除去後に評価、あるいは正規化パスで比較）へ強化し、将来の URL 変化での再 404 を防止。
- transform 経路側で `/derived/import/` を正式解決できるようにする恒久対応（現状はバイパスで責務が UI 側に寄っている）。これにより幅指定の responsive 配信も回復。
- `display.webp` 以外の import 派生物（今後追加され得る種別）が同様の 404 を起こさないかの棚卸し。

## 5. 最終推奨

**条件付き承認（Approve with one gate）**。

根本原因・修正方向・検証範囲・リスク遮蔽はホットフィックスとして妥当で、staging→production 投入に足ります。ただし **P0（ガード順序＝早期 return が制御文字/正規化ガードの後段にあること）をコード上で確認**することを投入の前提条件とします。これが担保済みであれば、exact-SHA ゲート通過を条件に staging・production へ承認可。§4 は本番投入後のフォローで可。
