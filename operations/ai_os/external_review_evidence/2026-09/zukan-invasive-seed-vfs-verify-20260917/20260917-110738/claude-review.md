## 1. 採用すべき点

- **フォールバックの方向性が正しい**：Node では `fileURLToPath(new URL(..., import.meta.url))` で正準シードを解決し、Cloudflare の非 file URL 例外を捕捉して VFS 側へ切り替える設計は、二つのランタイムの根本的な差（file URL の有無）を正面から扱っており妥当。
- **ドリフト防止のガードがある**：複製ファイルを SHA-256 等価テストで縛っている点は、二重ソース化の最大リスク（内容乖離）に対する直接的な防御で、コミット済み複製方式としては最低限の正解。
- **スコープが狭い**：マイグレーション・認証・権限・クロスプロダクト境界に触れておらず、対象データが外来種カタログ（公開参照データ、PII なし）である点も含め、リリース面の爆発半径は小さい。
- **契約テストと dry-run の両輪**：Wrangler contract test の更新と staging dry-run でのモジュール添付確認は、VFS materialization の実効性を経路レベルで裏付けており良い。

## 2. 重大な懸念

- **catch の粒度（最重要）**：「Cloudflare の invalid/non-file module URL を catch」とあるが、`try` が広すぎると Node 側の正当な I/O 失敗（ファイル欠落・権限）まで飲み込み、Node 実行中に存在しない `/bundle/runtime/...` を読みに行って二次失敗・不明瞭なエラーに化ける恐れがある。捕捉条件が「URL scheme / `ERR_INVALID_URL_SCHEME` 等の限定判定」か「無差別 catch」かで P0/P1 が分かれる。
- **glob の将来的な過剰取り込み**：`runtime/**/*.json` を `fallthrough:false` の Data ルールに追加したため、今後 `src/content/runtime/` 配下に置かれる任意の JSON が無条件で Worker バンドルへ同梱される。意図しない大容量ファイルや秘匿値が将来紛れ込む導線になり得る（現時点の内容ではなく運用上の穴）。
- **ビルド後のパス解決の検証範囲**：Node 側 14/14 pass は良いが、それが「本番と同じ実行レイアウト（例：`dist/` から起動）」で走っているかが本文からは読めない。`import.meta.url` 相対解決はコンパイル後の配置に依存するため、テスト構成＝本番構成でない場合は擦り抜ける典型パターン。

## 3. P0 で変更すべき仕様

現時点で**確定的な P0 ブロッカーは特定できていない**。ただし以下は「確認の結果次第で P0 に昇格」する条件付き項目です。

- **catch が無差別（`catch {}` 相当）である場合は P0**：Node 側の実 I/O エラーを握り潰さないよう、`err.code === 'ERR_INVALID_URL_SCHEME'`（および相当の非 file URL 判定）に限定し、それ以外は再スローすること。ここが広い catch なら本番 Node での障害隠蔽リスクがあるため修正必須。

## 4. P1 以降に回すべき仕様

- **複製ファイルを「生成物」として扱う**：手動コミットの複製ではなく、正準シードからの**ビルド時生成**（またはコピー）に切り替える。当面残すなら、複製ファイル先頭に `DO NOT EDIT — generated from db/seeds/...` を明記。等価テストは乖離を検出できても「どちらが正か」を示さないため、方向性を運用で固定する。
- **glob を最小化**：`runtime/**/*.json` ではなく `runtime/invasive_species_seed.ja.json`（または明示的許可リスト）へ絞り、将来ファイルの無自覚同梱を防ぐ。広い glob を維持するなら「runtime 配下は同梱前提」というルールをリポジトリに明文化。
- **本番相当レイアウトでのパス解決テスト**：ビルド成果物（`dist/` 等）からの Node 実行で正準シード解決が通ることを 1 ケース追加。
- **バンドルサイズの回帰監視**：シード JSON を同梱するため、Worker サイズ上限に対するマージンをテスト/CI で軽く監視できると安心。

## 5. 最終推奨

**条件付きで登録済み staging リリース前のマージ可**。ブロッカーの成否は 1 点、**フォールバック catch の粒度**に集約されます。

- catch が非 file URL に限定され Node の実エラーを再スローしているなら → **P0 なし、マージ可**。P1 項目（複製の生成物化・glob 最小化・本番レイアウトのパステスト）は後続で対応。
- catch が無差別なら → **マージ前に限定化を要修正（P0）**。

なお本変更のデータ・権限・プライバシー面のリスクは低く、二重ソース化は等価ガードで当面許容範囲。残る本質的な脆さは「握り潰し catch」と「広い glob の将来導線」の 2 点に尽きます。
